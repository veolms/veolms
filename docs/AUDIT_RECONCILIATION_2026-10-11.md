**Basis values.** `Traced` = conclusion from reading the code path. `Evaluated` = a schema or function was run in isolation. `Lint` = ESLint run. Every `OPEN_CONFIRMED` below is a code-reading conclusion unless the basis says otherwise; no finding was reproduced against a running system in this pass.

### Facts that apply to every finding

- **No automated tests exist.** Commit `7192af5b` (9 Oct) removed every unit test and all test tooling. `apps/api/package.json` has only `typecheck` and `build`. Existing coverage for every finding is therefore none, and there is no runner to add API regression cases to. See section 8.
- **Very little of the audit has been fixed.** The "launch audit" commits of 9 Oct mostly pre-date the audit's observations. Only `b93d686d` (F4/F9), `777fa2e4` (F1) and `dc7f3b24` (F17) changed anything in scope, all partially. No commerce, media, courses or auth-server finding was fixed after the audit.
- **Unmapped database errors return 500.** `packages/api-core/src/errors.ts:126-170` has no mapping for pg `23505`/`23503`. This is the root of C13, B3, C6b and several auth races.
- **`apps/api/AGENTS.md` lists "checking account existence before consuming an OTP" as ordering to preserve.** S6/A1 must therefore add a non-consuming code check, not reorder the existing consume call.

| Cloudflare only, by count                   | `1`                                                    | Only if the server refuses everything that does not come from Cloudflare. Otherwise a direct caller can forge the header. |
| Cloudflare, then a proxy on the same server | `loopback` followed by Cloudflare's ranges             | The local proxy must append the address it received from to `X-Forwarded-For`.                                            |
| Cloudflare, then a local proxy, by count    | `2`                                                    | Only with the same restriction to Cloudflare.                                                                             |

Why this blocks the push rather than following it: the per-address limits on sign-in codes added under S13 are counted in the database. If Node sees Cloudflare's addresses instead of visitors' (`TRUST_PROXY=false` with no local proxy), every visitor arriving through one Cloudflare location shares one allowance, and a busy hour stops sign-ups for all of them.

**To resolve the four.** On the API server, in the application directory (prints no secret):

```bash
grep -E '^(NODE_ENV|TRUST_PROXY|WEB_URL|CORS_ORIGINS|WEBAUTHN_ORIGINS|RP_ID)=' .env
```

```bash
sudo ss -ltnp | grep -E ':(80|443)\b'
```

Then list the custom domains on the Cloudflare worker and the CloudFront distribution, and run the count file against the production database (read-only; it returns two rows of counts and writes nothing):

```bash
psql "$PRODUCTION_DATABASE_URL" -x -f docs/audit-pre-push-checks.sql
```

**How to read the counts.** Check 3: if `restricted_free_courses` is 0, nothing changes for anyone. Otherwise the learner counts beside it are the people who lose that course's quizzes and lesson discussions unless they are given a grant first. **How the window works.** The web tells the gateway to close its checkout after 10 minutes (`CHECKOUT_WINDOW_SECONDS`). - After pressing Pay, they cannot change the amount or coupon for that purchase, or buy something that overlaps it, for up to 12 minutes. This holds even if they closed the payment window themselves, because the server cannot know it was closed. Paying the same amount works at once.
- A bundle cannot be bought by someone who owns one of its courses.
- While a reported transfer waits for staff, the buyer cannot pay for that purchase another way. A transfer left unanswered keeps that buyer blocked.

**What still cannot be stopped.** The app cannot refuse money at the bank. These stay on the staff refund list:

1. A payment completed on an old gateway order after the 12 minutes: a UPI request approved very late, or a tab still running a web build from before this release.
2. Two captures by the provider for one gateway order.
3. The same person buying through two different accounts.

## 30. P2, stylesheet loading: 14 Oct 2026

On `perf/critical-css`. The owner allowed a production build of the web, on condition that nothing is deleted without permission beyond the build's own output folder.

**What was wrong.** Every prerendered page linked two render-blocking stylesheets: `styles-*.css` (588 KB, 71 KB gzip) and `shell-theme-*.css` (130 KB, 22 KB gzip). 92% of the first is Tailwind utilities for the whole app. Nothing was inlined: the critical-CSS step described in `docs/performance-report.md` was removed on 17 Aug (commit `a85e78e20`), so that report is out of date on this point.

**What changed.** After the build, `apps/web/scripts/inline-critical-css.mjs` writes into each prerendered page the CSS rules that page can match, in the same cascade position, and makes the two large stylesheets non-blocking. The client waits for them before it hydrates (10 s budget), so nothing the app renders appears unstyled, then drops the inline copies. The dev server, the SPA fallback and course pages refreshed later by `refresh-course-static-pages.mjs` are unchanged.

**How it was verified.** A local production build against a local API on the demo database, then measured with Chromium on a mobile profile (4x CPU slowdown, 150 ms latency, 1.6 Mbit/s), median of 5 runs:

| Page            | First paint before | First paint after | CSS fetched before first paint |
| --------------- | ------------------ | ----------------- | ------------------------------ |
| `/`             | 1372 ms            | 904 ms            | 83 KB to 2 KB                  |
| `/courses`      | 1184 ms            | 756 ms            | 83 KB to 2 KB                  |
| Course overview | 1252 ms            | 756 ms            | 83 KB to 2 KB                  |
| `/login`        | 1132 ms            | 644 ms            | 69 KB to 7 KB                  |

Page load and hydration times are unchanged.

**Design unchanged.** Every prerendered page was compared pixel by pixel with the previous build, at 412x915 and 1366x900, light and dark. Each was compared with JavaScript off and full CSS, with JavaScript off and only the inline CSS (the first paint), and with the app hydrated. All were identical on the real build, for 17 of the 18 pages; the settings index was checked on a processed copy of the build. The one difference was lazy-loaded wallpaper images far below the fold on one settings page, with JavaScript off and the full page captured. Those images load at different moments in both builds, and the same page is identical at first paint.

**Trade-off.** Each page's HTML grows by 9 to 33 KB gzip, paid on every full page load, also by visitors who already have the stylesheets cached.

**Not verified.** Lighthouse itself, and the deployed site. The deploy builds through the same script (`pnpm build:web`), so the change ships with the normal build.
