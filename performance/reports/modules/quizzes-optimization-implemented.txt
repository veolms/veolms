QUIZ BACKEND OPTIMIZATION - IMPLEMENTED
=======================================

Scope: Quiz authoring, assignments, attempts and analytics.
Video processing, streaming and Fleet Manager were not changed.

FIXED QUERY PROBLEMS
--------------------

1. Quiz authoring list/detail
Before: loading every quiz separately; every version loaded questions and
options separately.
After: quiz versions, questions, options and assignments are batch loaded.
Result: query count no longer grows with the number of quizzes or versions in
the list endpoint.

2. Course quiz assignment list
Before: one quiz query for every assignment.
After: assignment and quiz title are loaded with one JOIN query.
Result: removed the assignment-level N+1 query pattern.

3. Assignment analytics
Before: one user query for every student.
After: all student display names are loaded with one batched Auth query.
Result: removed the student-level N+1 query pattern.

4. Course quiz analytics
Before: every assignment loaded its own active students, attempts, ownership
data and quiz title. The work multiplied by assignment count and student count.
After: assignments, quiz titles, active students and all attempts are loaded
in bulk. Reports are calculated in memory.
Result: course analytics now uses a small fixed number of database reads and
does not run one analytics workflow per assignment.

5. Learner quiz assignment list
Before: one quiz, lesson and active-attempt lookup per assignment, plus one
course lookup per course.
After: quiz titles use a JOIN; courses and lessons use batch lookups; active
attempts are selected from the already loaded user's attempts.
Result: removed multiple learner-side N+1 patterns.

6. Student quiz report
Before: repeated array scans to find attempts and quiz titles.
After: in-memory Maps are used for assignments, attempts and quiz titles.
Result: lower CPU work as the number of assignments grows.

7. Attempt presentation and grading
Before: repeated filtering of options/questions for every item.
After: options, questions and answers are grouped by ID once and reused.
Result: lower CPU work without changing the response contract or grading rules.

8. Version cloning during editing
Before: one insert query per copied question and per question's options.
After: questions and options are inserted in batches inside the same existing
transaction.
Result: fewer write queries while preserving version-copy behavior.

DATABASE INDEXES ADDED
----------------------
- quizzes by creator/academy, deleted state and updated time
- quiz questions by version, deleted state and position
- question options by question and position
- assignments by course/quiz and creation time
- attempts by assignment/user and creation time

These indexes match the filters and ORDER BY clauses used by the optimized
read paths. Existing indexes were not removed.

BEHAVIOR PRESERVED
------------------
- URLs, HTTP methods and operation IDs unchanged.
- Response shapes and contracts unchanged.
- Quiz ownership, academy checks, learner access, MFA and role checks kept.
- Attempt limits, expiry, grading, feedback and outbox behavior kept.
- Existing transaction boundaries for writes kept.
